# FPGA 网络结构对比：21 类 passthrough 最新任务 vs 历史 2 类任务

> 日期：2026-09-04  
> 最新 21 类任务：`20260904_031656_test_21_class_pipeline_03`  
> 上一版 21 类任务：`20260903_190838_test_21_class_pipeline_02`  
> 历史 2 类任务：`20260727_151741_aituosh_moon_0727_2`  
> 目的：给 FPGA 开发者说明从 2 类模型切到 21 类模型后，ONNX 输出结构、FPGA 权重/bin 包和后处理解析需要关注哪些变化。  
> 更新说明：本文档已根据最新任务刷新。最新任务是在修复 `PNG→bin→side_view→ONNX` 输入回环通道问题后重新跑通的版本。

## 0. FPGA 侧相比历史 aituosh 2 类任务的变化摘要

这一节先给结论，后文再展开证据和细节。

相比历史任务 `20260727_151741_aituosh_moon_0727_2`，最新 21 类任务对 FPGA 来说不是主干网络换代，主要变化集中在输入语义、输出通道、权重包读取和后处理。

### 0.1 输入尺寸不变，但灰度通道语义需要确认

网络输入 shape 仍然是：

```text
[1, 3, 1280, 1280]
```

但当前 21 类模型按 R-only 图像理解输入：

```text
R = gray
G = 0
B = 0
```

FPGA 侧需要确认：

1. 2000×2000×12bit 灰度图进入 FPGA 后，最终喂给网络的 1280×1280×3 通道图像，应把灰度值放到 R 通道。
2. G/B 通道应保持 0。
3. 不要再做一次 RGB/BGR 转灰度，否则 R-only 输入会被压暗到约 0.299 倍。

预期 FPGA 图像预处理流程：

```text
2000×2000×12bit grayscale
-> 12bit 到 8bit 线性缩放
-> 2×2 平均降采样到 1000×1000
-> 四周补 140 像素 0 padding
-> 1280×1280
-> 放入 R 通道，G/B 为 0
```

### 0.2 类别数从 2 变成 21，最终输出通道从 12 变成 31

历史 2 类任务：

```text
output0 = [1, 12, 34000]
12 = 4 bbox + 2 class + 6 keypoint
```

最新 21 类任务：

```text
output0 = [1, 31, 34000]
31 = 4 bbox + 21 class + 6 keypoint
```

候选数 `34000` 没变，变化的是每个候选框后面携带的类别分数数量。

### 0.3 后处理通道 offset 必须改

历史 2 类：

```text
ch0..3   = bbox
ch4..5   = class scores
ch6..11  = keypoint
```

最新 21 类：

```text
ch0..3    = bbox
ch4..24   = class scores
ch25..30  = keypoint
```

也就是说，不能再硬编码：

```text
nc = 2
output_channels = 12
keypoint_start = 6
```

应改为：

```text
nc = 21
output_channels = 31
keypoint_start = 4 + nc = 25
```

如果 FPGA 内部为了对齐按 32 通道处理，第 32 个通道只是 padding，不能参与类别最大值选择、阈值判断、NMS 或 keypoint 解析。

### 0.4 权重包大小和 L43 发生变化

历史 2 类：

```text
ALL_WT.bin = 100,205,568 bytes
无 L43_WT.bin
```

最新 21 类：

```text
ALL_WT.bin = 102,381,568 bytes
新增 workspace/renamed_weights_bin/T32_T32_L43_WT.bin
L43_WT.bin = 2,176,000 bytes
```

新增大小正好是：

```text
32 × 34000 × 1 × 2 bytes = 2,176,000 bytes
```

这里的 32 很可能对应“31 个有效输出通道 + 1 个 padding 对齐通道”。

因此 FPGA 侧不能继续按历史 2 类的 `ALL_WT.bin` 总大小或历史权重文件数量读取。

### 0.5 NMS 可以保留，但需要增加 21 类业务过滤

普通 YOLO NMS 仍然需要，用来去掉重叠候选框。

但 21 类业务和历史 2 类业务不同：

1. 历史 2 类：地标和月亮可能同时出现。
2. 最新 21 类：20 个地球地标互斥，同一视野中最多应保留 1 个地标；月亮可以和 1 个地标共存。

建议后处理顺序：

```text
34000 候选
-> score 阈值过滤
-> 普通 NMS
-> 业务过滤：20 个地标最多保留最高分的 1 个，月亮可单独保留
-> 输出最终结果
```

### 0.6 已验证的软件侧输入回环问题

上一版 21 类任务中，`fpga_input_roundtrip_eval` 精度低，是因为软件测试路径里 PNG→bin 时错误地对 R-only 图做了 `BGR2GRAY`。

最新任务已修复并验证：

```text
PT F1                  = 0.9420
ONNX F1                = 0.9420
FPGA input roundtrip F1 = 0.9420
```

这说明软件侧 `PNG→bin→side_view→ONNX` 已经和直接 ONNX 输入对齐。后续 FPGA 实机如果精度低，应优先检查实机预处理是否真的满足本节 0.1 的输入语义。

## 3. ONNX 网络结构对比

### 3.1 输入没有变化

两版 ONNX 的模型输入一致：

| 项 | 最新 21 类 | 历史 2 类 | FPGA 影响 |
|---|---|---|---|
| 输入名 | `images` | `images` | 不变 |
| 输入类型 | `FLOAT16` | `FLOAT16` | 不变 |
| 输入 shape | `[1, 3, 1280, 1280]` | `[1, 3, 1280, 1280]` | FPGA 仍按 3 通道 1280×1280 输入适配 |

结论：FPGA 侧网络输入尺寸没有因为 21 类发生变化。仍然需要确认 FPGA 是否把灰度数据放进 R 通道，并保持 G/B 为 0。

### 3.2 主干和计算图规模基本没有变化

对比的是交付包里的 `*_output.onnx`。

| 项 | 21 类 | 历史 2 类 | 说明 |
|---|---:|---:|---|
| ONNX 节点数 | 667 | 667 | 相同 |
| initializer 数 | 615 | 615 | 相同 |
| Conv 数 | 148 | 148 | 相同 |
| graph output 数 | 524 | 524 | 相同，都是为了 FPGA/bin 生成暴露中间层 |

结论：从 FPGA 计算主干角度看，这不是一次 YOLO 版本升级，也不是主干网络重构。网络主体层数、主要算子数量、特征图层级都没有变化。

### 3.3 Detect Head 的类别分支发生变化

YOLO Pose Detect Head 仍然有 4 个尺度输出：

```text
160×160 = 25600
80×80   = 6400
40×40   = 1600
20×20   = 400
合计候选数 = 34000
```

候选数没有变化，仍然是 34000。

Detect Head 中三类通道含义：

```text
box 通道：4
class 通道：nc
keypoint 通道：6
```

历史 2 类：

```text
output0 shape = [1, 12, 34000]
12 = 4 box + 2 class + 6 keypoint
```

最新 21 类：

```text
output0 shape = [1, 31, 34000]
31 = 4 box + 21 class + 6 keypoint
```

这就是最核心的网络结构变化。

### 3.4 最后一层各分支通道变化

| 分支 | 历史 2 类 | 最新 21 类 | 是否变化 |
|---|---:|---:|---|
| bbox / DFL 分支 | 每尺度 64 通道 | 每尺度 64 通道 | 不变 |
| class 分支 | 每尺度 2 通道 | 每尺度 21 通道 | 变化 |
| keypoint 分支 | 每尺度 6 通道 | 每尺度 6 通道 | 不变 |

因此 FPGA 侧如果有硬编码 class channel 数、final output channel 数、后处理 channel offset，都必须改。

## 4. 后处理解析变化

两版最终输出顺序仍然是：

```text
[bbox 4 通道] + [class nc 通道] + [keypoint 6 通道]
```

历史 2 类：

```text
ch0..3   = bbox
ch4..5   = class scores，共 2 类
ch6..11  = keypoint，共 6 通道
```

最新 21 类：

```text
ch0..3    = bbox
ch4..24   = class scores，共 21 类
ch25..30  = keypoint，共 6 通道
```

FPGA 开发者需要重点确认：

1. 后处理不能再按固定 12 通道解析。
2. 类别数 `nc` 应改为 21，最好做成参数。
3. keypoint 起始通道从 `6` 改成 `25`，即 `4 + nc`。
4. 单候选输出通道从 `12` 改成 `31`。
5. 候选数仍是 `34000`，NMS 遍历候选数量不需要变化。
6. 如果 FPGA 或 CPU 后处理为了对齐把通道 padding 到 32，需要明确实际有效通道只有 31，最后 1 个 padding 通道不能参与 class 或 keypoint 解析。

### 5.1 交付 zip 文件

|---|---:|---:|---:|

zip 文件数不能直接等价为网络层数变化，因为里面还包含测试结果、日志、清单等产物。判断 FPGA 网络结构应主要看 ONNX 和：

```text
workspace/all_bin

```

### 5.2 合并权重 `ALL_WT.bin`

| 项 | 最新 21 类 | 历史 2 类 | 差异 |
|---|---:|---:|---:|
| `workspace/all_bin/ALL_WT.bin` | 102,381,568 bytes | 100,205,568 bytes | +2,176,000 |
| `workspace/all_bin/ALL_BN.bin` | 169,088 bytes | 169,088 bytes | 不变 |
| 新增 L43 权重 | 有 | 无 | +1 |

最新 21 类任务比历史 2 类任务多出的权重文件：

```text
workspace/renamed_weights_bin/T32_T32_L43_WT.bin
size = 2,176,000 bytes
shape = [32, 34000, 1, 2]
offset in ALL_WT.bin = 100,205,568
```

这个大小正好等于：

```text
32 × 34000 × 1 × 2 bytes = 2,176,000 bytes
```

这里的 32 很可能是 FPGA 侧对 31 个有效输出通道做了对齐 padding：

```text
31 有效通道 = 4 bbox + 21 class + 6 keypoint
padding 到 32 通道
```

历史 2 类交付包没有 `L43_WT.bin`。FPGA 开发者不能只按历史 2 类的权重文件数量或历史总权重大小读取。

### 5.3 L42 之前保持一致

两版最后常规卷积层到 L42 的权重 offset 和 shape 一致，例如：

```text
L42_s00: {96, 640, 3, 3, offset 99566592, size 552960}
L42_s01: {96, 96, 3, 3, offset 100119552, size 82944}
L42_s02: {32, 96, 1, 1, offset 100202496, size 3072}
```

历史 2 类的 `TOTAL_WEIGHT_SIZE` 到这里结束：

```text
TOTAL_WEIGHT_SIZE = 100,205,568
```

最新 21 类在 L42 后追加 L43：

```text
L43_WT offset = 100,205,568
L43_WT size   = 2,176,000
TOTAL_WEIGHT_SIZE = 102,381,568
```

BN 表没有新增 L43：

```text
TOTAL_BN_SIZE = 169,088
```

说明 L43 不是普通 Conv+BN 层，更像是为了 FPGA 输出/后处理适配打包的附加数据。

## 6. 输入回环问题的定位和修复

上一版 21 类任务 `20260903_190838_test_21_class_pipeline_02` 中，直接 ONNX 的 F1 是 0.9420，但 `fpga_input_roundtrip_eval` 的 F1 只有 0.5872。

问题定位到 `png_bin_converter.py` 的历史行为：

1. PNG→bin 时总是执行 `BGR2GRAY`。
2. 对已经是 `R=gray,G=B=0` 的 passthrough 输入，`BGR2GRAY` 会把亮度压到约 `0.299 × R`。
3. bin→PNG side_view 又保存为三通道同值灰度。
4. 结果是 direct ONNX 输入和 roundtrip ONNX 输入语义不一致。

已按 passthrough 模式修复：

1. PNG→bin：取源图 R 通道作为灰度源，不再 BGR2GRAY。
2. bin→PNG side_view：保存为 `R=gray,G=B=0`。
3. `04_generate_fpga_test_pack.py`：向转换函数传递 `job_config.preprocess_mode`。

最新任务验证结果：

```text
PT F1                       = 0.9420
ONNX F1                     = 0.9420
FPGA input roundtrip F1      = 0.9420
```

因此，软件侧 `PNG→bin→side_view→ONNX` 回环路径已经和直接 ONNX 路径对齐。

## 7. 给 FPGA 开发者的变更清单

### 必须确认 / 修改

1. 输入仍是 `[1, 3, 1280, 1280]`，但数据语义必须确认：
   - 当前 21 类任务使用 `passthrough`；
   - 对 R-only 图，应保持 `R=gray, G=B=0`；
   - 不应额外做 RGB/BGR 转灰度，否则可能把亮度压成 0.299 倍。

2. 最终输出解析从 12 通道改为 31 通道：
   - 老：`4 + 2 + 6 = 12`
   - 新：`4 + 21 + 6 = 31`

3. 如果 FPGA 内部按 32 通道对齐：
   - 有效通道是 31；
   - 第 32 个通道是 padding；
   - padding 不能参与类别最大值选择、阈值判断或 NMS。

4. class 分支每尺度输出从 2 通道变成 21 通道：
   - 160×160、80×80、40×40、20×20 四个尺度都变化；
   - 候选数仍是 34000。

5. 后处理 channel offset 必须改：
   - bbox：`0..3`
   - class：`4..24`
   - keypoint：`25..30`

6. NMS 逻辑需要适配 21 类业务规则：
   - 普通 YOLO NMS 可以保留；
   - 但地球 20 个地标互斥，月亮可与一个地标共存；
   - NMS 后建议增加业务过滤：最多保留一个地标类别，再可保留月亮。

7. 读取权重总包时不能硬编码旧大小：
   - 旧 `ALL_WT.bin`：100,205,568 bytes；
   - 新 `ALL_WT.bin`：102,381,568 bytes；
   - 新增 `L43_WT.bin`，offset 从旧总大小位置开始。

8. FPGA 实机输入预处理应和当前软件回环一致：
   - 12bit 灰度到 8bit：线性缩放，不右移；
   - 2000×2000 到 1000×1000：2×2 取平均；
   - padding：四周固定补 0，宽度 140；
   - padding 后输入：1280×1280；
   - 后处理坐标还原：需要减去 140 padding。

### 理论上不需要改

1. 输入 tensor shape 没变。
2. 主干 Conv 层数量没变。
3. 常规 L00–L42 的权重 shape/offset 基本没变。
4. 候选框数量仍是 34000。
5. keypoint 通道数量仍是 6。
6. bbox/DFL 分支仍是 64 通道。

## 8. 当前遗留风险

1. 软件输入回环低精度问题已关闭。

   最新任务已经证明 `PNG→bin→side_view→ONNX` 与 direct ONNX 指标一致。

2. 仍需在 FPGA 实机确认输入语义。

   当前软件已按 `R=gray,G=B=0` 统一，但 FPGA 之前适配过彩图模型，因此需要确认实机端没有再做一次 RGB/BGR 转灰度、通道复制或通道顺序交换。

3. 历史 2 类任务是旧交付包状态。

   如果用当前新版生成脚本重跑旧模型，是否也会生成 L43，需要单独验证。本文只比较“历史 2 类交付产物”和“当前 21 类交付产物”。

4. 21 类业务过滤尚未落地到最终交付后处理。

   当前结构适配和普通 NMS 可以跑通，但 20 个地球地标互斥、月亮可共存的业务规则仍需要在后处理设计中明确实现位置。

---

## 9. 一句话结论

对 FPGA 开发者来说，这次从 2 类到 21 类不是主干网络换代，核心变化是 Detect 输出头的类别通道从 2 增到 21，最终输出从 `[1,12,34000]` 变成 `[1,31,34000]`，并且交付包新增了对齐到 32 通道的 `L43_WT.bin`。最新任务已经验证输入回环精度恢复，FPGA 侧最需要改的是最终输出通道解析、类别数、keypoint 起始 offset、权重总包读取大小、R-only 输入语义，以及 NMS 后的 21 类业务过滤规则。
