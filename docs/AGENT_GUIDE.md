# 如何使用 Agent 维护量化平台

面向需要让 Codex 或其他自动化 Agent 协助排查、操作、备份和开发的同事。

## 1. Agent 能做什么

适合交给 Agent：

- 只读检查服务、任务、GPU、磁盘、NAS 和日志。
- 根据证据定位任务卡住、容器异常或路径错误。
- 在明确授权后重启量化服务、更新项目文件、创建备份。
- 修改代码并执行有边界的回归测试。
- 维护操作文档和进度记录。

不应含糊交给 Agent：

- “找张空闲卡随便跑”——公用服务器需要明确资源检查和协调。
- “把没用的数据删掉”——必须给出路径、保留期、验证和回滚规则。
- “把服务器升级一下”——驱动、内核、Docker 和 APT 会影响其他用户。
- 在提示词中粘贴密码——密码只应交互输入或放在权限受控的凭据文件中。

## 2. 每次任务都使用的提示词骨架

复制下面模板，替换尖括号内容：

```text
请先阅读本机 E:\codex\quantitize\AGENTS.md，
再阅读 docs/agent/CONTEXT.md 和 docs/agent/RUNBOOK.md。

目标：<要达成的结果>
范围：<允许访问或修改的主机、目录、服务>
禁止事项：<例如不使用 GPU、不停止其他用户进程、不修改系统包>
验收标准：<成功必须看到的状态、文件、指标或返回值>

开始时先做只读检查并报告判断依据。
如果需要扩大权限、修改全局配置、删除数据或使用未分配 GPU，先停止并说明。
执行期间持续更新进度；结束时给出实际变更、验证结果和剩余风险。
```

一个好的提示词应包含“目标、范围、禁止事项、验收标准”，而不只是一个动作。

## 3. 常用提示词

### 3.1 检查平台是否正常

```text
请先阅读 AGENTS.md、docs/agent/CONTEXT.md 和 RUNBOOK.md。
只读检查 H200 量化平台：SSH、Docker Compose、API/Web health、GPU readiness、磁盘空间和最近任务状态。
不要重启服务，不要启动 GPU 任务，不要修改任何文件。
按“正常、异常、风险、建议下一步”输出，并附关键命令证据。
```

### 3.2 检查某个量化任务

```text
只读检查 H200 任务 <task_id>。
确认总状态、当前阶段、runner/子进程、最近更新文件、阶段日志、GPU/CPU 使用和错误字段。
区分“正在计算、等待 GPU、已失败、进程消失但状态未更新”。
不要停止或重启任务。给出当前进度、判断证据和下一次检查建议。
```

### 3.3 在共享服务器上选择 GPU

```text
连续采样 H200 四张 GPU 的利用率、显存、功耗和计算进程，并查询进程所属用户及运行时长。
只读，不启动任务，不停止任何进程。
推荐一张适合 <预计显存> 的卡；如果没有真正空闲的卡，明确说明需要协调，不要强行推荐。
```

### 3.4 安全重启平台

```text
按 docs/agent/RUNBOOK.md 的 service_restart 执行 H200 量化平台重启。
先确认没有 running/waiting_gpu 任务；如有任务则停止并报告，不要重启。
只操作 /data3/ywang/quantitize-platform 的两个 Compose 服务，不使用 down -v。
验收：两个容器 healthy，8000/8088 health 成功，现有历史任务仍可查询。
```

### 3.5 备份系统但排除历史输出

```text
为 H200 量化平台创建新的 NAS 不可变快照。
包含代码、shared_data、重建资料、API/Web 镜像、环境和主机清单；排除 data/output_data。
大文件写入 .partial，成功后原子改名；生成 SHA256SUMS 并执行 zstd/gzip 完整性测试。
不得覆盖已有 VERIFIED 快照，不得记录 NAS 密码。
完成后更新 BACKUP_STATUS 和 Agent context。
```

### 3.6 设计 output_data 归档清理

```text
先只读分析 /data3/ywang/quantitize-platform/data/output_data 的目录结构、大小、最后修改时间和运行中任务。
设计按顶层 task_id 归档到 NAS 的方案：连续 14 天无修改才归档，校验后保留 7 天宽限期再清理本地。
失败或未完成任务默认不自动删除；NAS 不可用、空间不足或校验失败时绝不清理。
先给 dry-run 和验收方式，不直接删除数据。
```

### 3.7 修改代码或优化性能

```text
阅读 docs/reference/PERFORMANCE.md 和项目 pipeline/FLOW.md。
目标：<具体优化点>。
先建立固定模型、标定集、测试集、镜像 ID 和阶段耗时基线。
只修改 <文件范围>，不得修改业务指标定义。
执行最小单元验证、阶段验证和固定 golden task 回归；比较速度、指标、文件清单和哈希。
若需要占用 GPU 或 /data1 NVMe，先报告资源和容量门禁。
```

## 4. 怎样判断 Agent 的回答可靠

可靠的回答应包含：

- 当前时间和目标主机，而不是只复述旧文档。
- 真实命令输出或文件证据。
- 明确区分事实、推断和建议。
- 变更前后对比及验收结果。
- 对公用服务器、GPU 冲突、NAS 校验和删除风险的说明。

需要追问的信号：

- 只看到 `GPU-Util=0%` 就说 GPU 空闲。
- API `health` 成功就说 GPU 已就绪；应同时看 `/ready`。
- manifest 阶段为 `pending` 就说没有运行；还应看子进程和 CPU/GPU。
- 备份只说“复制完成”，没有 SHA-256 和归档格式测试。
- 建议删除 lock 文件、`down -v`、停止陌生用户进程或修改全局驱动。

## 5. Agent 文档为什么只有两本

Agent 不需要阅读迁移流水账。它只需：

1. `agent/CONTEXT.md`：稳定事实和当前状态。
2. `agent/RUNBOOK.md`：按任务执行的门禁、命令和验收。

灾难恢复、环境重建和性能优化只有在触发相应任务时再读取。这样可减少上下文噪声，避免旧 TODO 和旧路径覆盖当前事实。
